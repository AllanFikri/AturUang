- membuka API finansial tanpa autentikasi;
- mengekspos app publik sebelum auth/session/CSRF/rate guard lulus;
- menyimpan backup atau secrets di Git;
- mengaktifkan auto-approval longgar;
- membuat tag/release publik tanpa instruksi pengguna;
- mengubah formula finansial Prompt 11 dan Prompt 12.

A. PRE-CUTOVER FREEZE DAN BACKUP
1. Tetapkan maintenance window singkat dan hentikan server lokal/write input.
2. Catat HEAD, hash dinamis, integrity/FK, logical fingerprint lengkap, dan waktu cutoff WIB.
3. Buat backup kanonis SQLite via backup_db() dan verifikasi dapat dipulihkan.
4. Ekspor D1 shadow sebelum final sync.
5. Identifikasi raw event/candidate setelah snapshot awal agar tidak hilang.

B. PORT WRITE-PATH PRODUKSI
Port seluruh operasi yang digunakan UI, bukan hanya happy path:
1. create/edit/reversal/delete transaction;
2. transfer internal;
3. reconcile/anchor/snapshot;
4. accounts;
5. budgets/categories;
6. upcoming create/link/unlink/skip/pay;
7. allocation goals fund/release/spend;
8. debts and debt events;
9. ingestion approval/apply;
10. idempotency requests;
11. audit logs.
Gunakan D1 batch/transaction semantics yang benar sehingga operasi multi-tabel atomik. Semua route mutasi wajib idempotency key, validasi state, dan audit event.

C. AUTH PRODUCTION TANPA LAYANAN BERBAYAR
1. Gunakan Telegram allowlisted sebagai faktor login dashboard:
   - browser meminta one-time code;
   - pengguna mengonfirmasi kode melalui bot;
   - code satu kali, short-lived, hashed, dan terikat browser attempt;
   - Worker menerbitkan session cookie HttpOnly, Secure, SameSite=Strict.
2. Terapkan session expiry/revoke, CSRF protection pada semua write request, origin validation, login throttling, dan generic error.
3. Sediakan recovery credential offline sekali pakai, tampilkan hanya saat setup dan jangan log/commit.
4. Health publik hanya mengembalikan status umum tanpa saldo/schema detail.

D. FRONTEND ONLINE SATU SUMBER
1. Gunakan frontend Vanilla JS/CSS yang sama, bukan membuat dashboard Tailwind/Apps Script baru.
2. Refactor static assets ke satu direktori bersama bila diperlukan sehingga lokal dan cloud tidak memiliki dua UI yang divergen.
3. Utamakan Workers Static Assets dan same-origin API untuk menghindari CORS/cookie complexity. Gunakan Pages hanya bila ada batas teknis yang dibuktikan.
4. Hilangkan endpoint localhost hardcoded; gunakan relative API origin.
5. Pertahankan responsive UI, format Rupiah, ARIA, focus trap, loading, istilah kanonis, no-cache untuk shell versi baru, dan version marker.
6. Tambahkan halaman/status koneksi yang jujur: Online, Sinkronisasi tertunda, Connector stale, atau Offline read-only.

E. FINAL SYNC DAN CUTOVER
1. Buat final export SQLite setelah freeze.
2. Import delta secara idempoten ke D1.
3. Rekonsiliasi raw/candidate connector yang tiba selama freeze.
4. Jalankan logical parity lengkap lagi.
5. Ubah MODE shadow menjadi production hanya jika seluruh gate lulus.
6. Aktifkan write routes dan ingestion apply secara bersamaan setelah cutover marker tercatat.
7. Local START_MONEY_TRACKS.bat tidak boleh membuka server write lama. Ubah menjadi pembuka URL cloud atau beri nama launcher lokal sebagai emergency-read-only.
8. Jangan menghapus folder/repository/database lokal.

F. INGESTION PRODUCTION
1. Candidate high-confidence sesuai aturan 13B boleh AutoApproved dan Applied tepat sekali.
2. Candidate lain masuk review Telegram/dashboard.
3. Approval membuat transaksi melalui service kanonis yang sama dengan UI manual.
4. Bila posting gagal, state tetap retryable dan tidak menandai Applied.
5. Auto-post selalu mengirim ringkasan Telegram dengan tombol koreksi/reversal, bukan silent mutation.

G. SCHEDULER DAN NOTIFIKASI
Gunakan Cloudflare Cron/trigger yang relevan untuk:
1. source stale check;
2. upcoming due reminder;
3. daily pending review digest;
4. forecast 7 hari ringkas;
5. backup health check;
6. cleanup nonce/session/idempotency retention.
Semua jadwal menggunakan Asia/Jakarta dan idempoten. Hindari notifikasi saat tidak ada perubahan.

H. BACKUP DAN RECOVERY
1. Gunakan D1 Time Travel bila tersedia pada plan aktif, tetapi jangan menjadikannya satu-satunya backup.
2. Buat logical export berkala melalui workflow/cron resmi, enkripsi sebelum penyimpanan, dan jangan commit file backup.
3. Sediakan manual download backup dari dashboard yang memerlukan re-auth.
4. Tetapkan retensi yang masuk akal dan dokumentasikan recovery point.
5. Recovery drill pada database/environment temporary harus membuktikan row count, aggregate, balances, goals, debts, transactions, candidates, dan idempotency identik.

I. OBSERVABILITY DAN PRIVASI
1. Log hanya request ID, route, status, latency, safe error code, parser version, dan event ID tersamarkan.
2. Dilarang log deskripsi transaksi, email body, token, cookie, nomor rekening, Telegram payload mentah, atau saldo penuh.
3. Tambahkan alert Telegram untuk repeated auth failure, connector stale, backup gagal, dan invariant failure.
4. Sediakan /health internal terautentikasi untuk schema version, last backup, last source sync, dan queue count.

J. TEST DAN RELEASE GATE
Wajib menguji minimal:
1. Seluruh write-path parity lokal vs D1 pada database temporary.
2. Atomic rollback setiap operasi multi-tabel.
3. Concurrent duplicate idempotency.
4. Reconciliation dan balance reconstruction.
5. Formula Prompt 11 dan insight Prompt 12.
6. Ingestion auto/pending/reject/reversal.
7. Telegram login code replay/expiry/wrong user.
8. CSRF, CORS/origin, session revoke, brute-force throttle.
9. Static assets/API same version.
10. Desktop dan mobile browser.
11. Recovery drill.
12. Final SQLite–D1 logical parity pada cutoff.
13. Seluruh regression suite lokal.
14. Tidak ada secret/PII dalam git diff dan logs.

K. GITHUB DAN DEPLOYMENT
1. Jadikan repository GitHub satu-satunya source code cloud.
2. Aktifkan deployment hanya setelah branch/config/build command benar dan staging pass.
3. Production deployment harus berasal dari commit terverifikasi, bukan dashboard editor.
4. Simpan Cloudflare credentials hanya di encrypted GitHub/Cloudflare secrets dengan least privilege.
5. Uji rollback ke deployment sebelumnya tanpa memulihkan data secara destruktif.

L. DOKUMENTASI DAN COMMIT
1. Perbarui spec, audit, roadmap, cloud runbook, incident response, backup/restore, dan user guide.
2. Commit yang disarankan bila lulus:
   feat(cloud): port write path dan autentikasi production
   chore(release): cutover Money Tracks ke Cloudflare D1
   docs(release): catat runbook cloud dan recovery
3. Jangan membuat tag tanpa instruksi pengguna.

STOP CONDITION:
Satu mismatch nominal >=0,005, route tak terlindungi, atomicity gagal, connector duplicate, backup tak dapat dipulihkan, atau local DB termutasi tak terencana membatalkan cutover. Pertahankan MODE=shadow dan laporkan blocker.

FORMAT JAWABAN MAKSIMAL 400 KATA:
Verdict; backup/freeze; parity; auth; frontend; ingestion; scheduler; recovery; tests; deployment URL tanpa secret; commits; local DB status; manual HP check; blocker.


PROMPT 17 — TUJUAN KEUANGAN, RENCANA KONTRIBUSI, DAN PENUTUPAN BULANAN

MODE IMPLEMENTASI PRODUK TERBATAS + HEMAT TOKEN.

Prasyarat:
- Prompt 14 PASS dan D1 sudah menjadi sumber kebenaran tunggal.
- Connector Gmail/Telegram sehat.
- Backup dan rollback teruji.

Tujuan:
Membantu pengguna merencanakan Dana Darurat, tujuan jangka pendek/panjang, dan komitmen rutin tanpa mencampur target dengan uang yang benar-benar dialokasikan; sekaligus menyediakan monthly close yang menjaga ledger dapat diaudit.

Jangan:
- mengurangi Dana Tersedia hanya karena target dibuat;
- menganggap piutang sebagai aset likuid;
- membuat transaksi, transfer, atau kontribusi otomatis tanpa konfirmasi;
- mengubah histori in-place setelah bulan ditutup;
- memaksa target Pernikahan atau target lain dibuat tanpa input pengguna;
- membuat investasi/rekomendasi finansial personal otomatis;
- menggunakan ML;
- merusak formula Prompt 11.

A. KONTRAK TUJUAN KEUANGAN
1. Bedakan:
   - target_amount: jumlah yang ingin dicapai;
   - allocated_amount: uang yang benar-benar dialokasikan;
   - funding plan: rencana kontribusi masa depan;
   - linked account: lokasi uang, bukan sumber status alokasi.
2. Hanya allocated_amount yang mengurangi Dana Tersedia.
3. Transfer antar Owned account netral terhadap Total Aset dan alokasi.
4. Fund/release/spend goal harus berupa allocation event append-only dengan audit trail dan idempotency.
5. Goal kind minimum: Emergency, ShortTerm, LongTerm, dan SinkingFund.
6. Status minimum: Draft, Active, Paused, Completed, Cancelled.

B. RENCANA KONTRIBUSI
1. Pengguna dapat memilih target date, nominal target, allocated awal, frekuensi, dan kontribusi rencana.
2. Sistem menghitung kebutuhan kontribusi per minggu/bulan, gap, progress, dan perkiraan tanggal tercapai.
3. Hasil adalah saran, bukan pemindahan uang otomatis.
4. Bila kemampuan dana tidak cukup, tampilkan selisih dan opsi menurunkan nominal/memperpanjang waktu; jangan menyatakan gagal.
5. Dana Darurat memakai milestone bertahap yang dapat dikonfigurasi, bukan angka universal yang dipaksakan.

C. KAITAN DENGAN KOMITMEN DAN FORECAST
1. Goal linked ke upcoming mengurangi komitmen efektif hanya sebesar allocated coverage aktif.
2. Hindari double deduction antara goal allocation, upcoming, dan forecast.
3. Tentative reserve_now=0 tetap tidak memotong Dana Tersedia.
4. Forecast 7/30 hari menunjukkan planned contribution terpisah dari confirmed commitment.
5. Pembayaran komitmen yang covered mengonsumsi allocation secara atomik dan menjaga invarian Dana Tersedia sesuai kontrak.

D. MONTHLY CLOSE
Sebelum bulan ditutup, checklist wajib:
1. semua sumber menunjukkan freshness yang dapat diterima atau diberi acknowledgement;
2. seluruh Owned account direkonsiliasi atau memiliki alasan belum;
3. pending ingestion direview atau ditunda secara eksplisit;
4. duplicate/invariant check bersih;
5. commitments, debts, titipan, dan goals diverifikasi;
6. monthly income/expense/category aggregate disimpan sebagai snapshot laporan;
7. backup berhasil.

E. LOCK, REOPEN, DAN BACKDATED EVENT
1. Setelah close, data bulan tidak boleh diedit in-place.
2. Koreksi memakai reversal/correction event dengan audit trail.
3. Reopen memerlukan re-auth, alasan wajib, timestamp, dan audit log.
4. Backdated transaction ke bulan closed harus ditolak atau melalui controlled reopen; jangan diam-diam mengubah laporan.
5. Closing ulang membuat versi baru, tidak menghapus snapshot lama.

F. UI
1. Tambahkan halaman atau subhalaman "Rencana" hanya bila audit navigasi membuktikan perlu; alternatifnya integrasikan ke Anggaran/Lainnya tanpa duplikasi.
2. Tampilkan:
   - Dana Darurat;
   - tujuan aktif;
   - progress funded vs target;
   - kebutuhan kontribusi;
   - upcoming terkait;
   - forecast impact;
   - status monthly close.
3. Bedakan jelas "Target", "Sudah Dialokasikan", dan "Rencana Setoran".
4. Gunakan nominal utuh, format Rupiah, mobile responsive, accessible labels, loading, empty/error state.
5. Jangan menggunakan progress bar yang menyesatkan saat allocated > liquid balance atau data stale; tampilkan warning.

G. TELEGRAM
Tambahkan command/aksi aman:
1. /rencana untuk ringkasan tujuan;
2. /alokasi untuk membuat draft allocation yang harus dikonfirmasi;
3. /tutupbulan untuk menampilkan checklist, bukan langsung menutup;
4. Approve close hanya setelah re-auth dan seluruh gate lulus;
5. Jangan menampilkan data sensitif ke chat selain allowlisted.

H. TEST WAJIB
Buat suite yang menguji minimal:
1. target tanpa allocation tidak mengurangi Dana Tersedia.
2. funding/release/spend goal akurat dan idempoten.
3. transfer antar Owned netral.
4. partial coverage dan anti-double deduction upcoming.
5. tentative reserve_now=0.
6. planned contribution hanya forecast.
7. goal complete/cancel/pause transitions.
8. close ditolak bila pending/freshness/reconciliation/backup gate gagal.
9. close berhasil membuat immutable versioned snapshot.
10. edit bulan closed ditolak.
11. correction/reopen memiliki audit trail.
12. timezone dan batas bulan WIB.
13. concurrency dan atomic rollback.
14. Telegram command authorization/idempotency.
15. seluruh KPI finansial dan historical reports tidak berubah tanpa event sah.
16. recovery dari backup mempertahankan close snapshots dan allocation events.

I. DOKUMENTASI DAN COMMIT
1. Perbarui spec, audit, roadmap, user guide, dan monthly-close runbook.
2. Commit hanya setelah seluruh test cloud dan lokal hijau:
   feat(planning): tambah tujuan keuangan dan monthly close
   docs(planning): catat aturan tujuan dan penutupan periode
3. Jangan membuat target finansial produksi atas nama pengguna pada tahap implementasi; gunakan fixture temporary.

STOP CONDITION:
Jika target non-funded mengurangi Dana Tersedia, bulan closed masih dapat diedit tanpa audit, goal/upcoming terpotong dua kali, atau produksi berubah karena test, jangan commit dan laporkan blocker.

FORMAT JAWABAN MAKSIMAL 350 KATA:
Verdict; contract tujuan; monthly close; UI/Telegram; tests; backup/integritas; files; commits; manual checks; blocker.
